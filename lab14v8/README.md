# Лабораторна робота №14
**Тема:** Аналіз SRP/OCP у відкритих репозиторіях.

---

## 1. Обрані open-source репозиторії

Для дослідження обрано два популярні open-source проєкти на мові C# із різних предметних областей:

1. **Serilog** (`https://github.com/serilog/serilog`) — інфраструктурна бібліотека для структурованого логування подій у застосунках .NET.
2. **eShopOnWeb** (`https://github.com/dotnet-architecture/eShopOnWeb`) — еталонний вебзастосунок електронної комерції (E-Commerce) на базі ASP.NET Core та Clean Architecture.

## 2. Аналіз прикладів SRP та OCP

### 2.1. Два приклади вдалого застосування SRP (Single Responsibility Principle)

#### Приклад 1: Клас `JsonFormatter` (Serilog)
* **Посилання:** [`src/Serilog/Formatting/Json/JsonFormatter.cs` (рядки 26–130)](https://github.com/serilog/serilog/blob/dev/src/Serilog/Formatting/Json/JsonFormatter.cs#L26-L130)
* **Де видно принцип:** Клас `JsonFormatter` має єдину зону відповідальності — перетворення об'єкта `LogEvent` у текстове JSON-представлення та запис його в абстрактний потік `TextWriter` у методі `Format(LogEvent logEvent, TextWriter output)`. Він не відповідає за відкриття файлів, мережеву відправку чи фільтрацію рівнів логування.
* **Переваги для підтримки:** Код ізольований, легко покривається модульними тестами (достатньо передати `StringWriter` у метод `Format`) і не змінюється при зміні способів доставки логів.
* **Що зміниться при додаванні нової функції:** Якщо знадобиться додати підтримку нового формату виводу (наприклад, XML або YAML), клас `JsonFormatter` не доведеться редагувати — достатньо створити окрему реалізацію інтерфейсу `ITextFormatter`.

#### Приклад 2: Клас `OrderService` (eShopOnWeb)
* **Посилання:** [`src/ApplicationCore/Services/OrderService.cs` (рядки 19–56)](https://github.com/dotnet-architecture/eShopOnWeb/blob/master/src/ApplicationCore/Services/OrderService.cs#L19-L56)
* **Де видно принцип:** Клас `OrderService` відповідає виключно за бізнес-сценарій оформлення замовлення (`CreateOrderAsync`): отримання кошика покупця, формування позицій замовлення з актуальними цінами товарів із каталогу та збереження замовлення. Робота з БД, SQL-запити та формування HTTP-відповідей винесені в репозиторії `IRepository<T>` та контролери.
* **Переваги для підтримки:** Бізнес-логіка формування замовлення зосереджена в одному місці й не залежить від деталей збереження даних у СУБД чи інтерфейсу користувача.
* **Що зміниться при додаванні нової функції:** При додаванні нової бізнес-вимоги (наприклад, розрахунку знижки під час оформлення замовлення) зміни торкнуться лише бізнес-правил у `OrderService` або окремого сервісу знижок, не зачіпаючи шар доступу до даних чи вебконтролери.

### 2.2. Два приклади порушення SRP

#### Приклад 1: Клас `LoggerConfiguration` (Serilog)
* **Посилання:** [`src/Serilog/LoggerConfiguration.cs` (рядки 20–240)](https://github.com/serilog/serilog/blob/dev/src/Serilog/LoggerConfiguration.cs#L20-L240)
* **Де видно порушення:** Клас поєднує роль зберігача конфігураційних колекцій (`_logEventSinks`, `_auditSinks`, `_enrichers`, `_filters`, `_overrides`), налаштування правил деструктуризації об'єктів (`Destructure`), управління мінімальними рівнями логування (`MinimumLevel`) та безпосередню фабричну збірку складного графа об'єктів у методі `CreateLogger()` (обгортання приймачів у `SafeAggregateSink`, `AggregateSink`, `FilteringSink`).
* **Ризики для підтримки:** Клас має багато причин для змін (поява нових механізмів фільтрації, зміна правил ініціалізації аудиту, нові параметри деструктуризації), що ускладнює його читання, розширення та модульне тестування окремих етапів конфігурування.
* **Що зміниться при додаванні нової функції:** При додаванні нового етапу обробки подій у конвеєрі (наприклад, асинхронної буферизації або нового типу перехоплювача) доведеться модифікувати як поля конфігурації, так і громіздку логіку методу `CreateLogger()`.

#### Приклад 2: Точка входу `Program.cs` (eShopOnWeb)
* **Посилання:** [`src/Web/Program.cs` (рядки 1–135)](https://github.com/dotnet-architecture/eShopOnWeb/blob/master/src/Web/Program.cs#L1-L135)
* **Де видно порушення:** В одному файлі верхнього рівня зосереджено одразу кілька різних відповідальностей: конфігурація постачальників баз даних (InMemory та SQL Server), реєстрація сервісів у DI-контейнері, налаштування ASP.NET Core Identity та політик Cookie, запуск ініціалізації та наповнення бази даних початковими даними (`CatalogContextSeed.SeedAsync`, `AppIdentityDbContextSeed.SeedAsync`), а також конфігурація конвеєра HTTP middleware.
* **Ризики для підтримки:** Файл швидко розростається зі збільшенням кількості модулів застосунку, а змішування налаштувань інфраструктури, безпеки та ініціалізації БД підвищує ризик конфліктів під час командної розробки.
* **Що зміниться при додаванні нової функції:** Підключення нового платіжного шлюзу, кешування або фонових сервісів вимагатиме чергового редагування спільного файлу `Program.cs`.

### 2.3. Два приклади дотримання OCP (Open/Closed Principle)

#### Приклад 1: Інтерфейс `ILogEventSink` (Serilog)
* **Посилання:** [`src/Serilog/Core/ILogEventSink.cs` (рядки 18–30)](https://github.com/serilog/serilog/blob/dev/src/Serilog/Core/ILogEventSink.cs#L18-L30)
* **Де видно принцип:** Ядро бібліотеки `Serilog` закрите для модифікації, але відкрите для розширення завдяки мінімалістичному контракту `ILogEventSink` із єдиним методом `void Emit(LogEvent logEvent)`. Усі механізми запису логів (у консоль, файл, базу даних чи хмарні сервіси) реалізуються як окремі класи-плагіни, що реалізують цей інтерфейс.
* **Переваги для підтримки:** Розробники можуть створювати власні або сторонні пакети (`Serilog.Sinks.File`, `Serilog.Sinks.Seq` тощо) без доступу до вихідного коду ядра бібліотеки та без ризику зламати існуючий функціонал.
* **Що зміниться при додаванні нової функції:** Для відправки логів у нове сховище (наприклад, у Telegram або Elasticsearch) достатньо створити новий клас із реалізацією `ILogEventSink` та метод розширення для `LoggerSinkConfiguration` — жоден існуючий файл у `Serilog` не змінюється.

#### Приклад 2: Патерн Specification через `ISpecification<T>` та `BaseSpecification<T>` (eShopOnWeb)
* **Посилання:** [`src/ApplicationCore/Specifications/BaseSpecification.cs` (рядки 7–55)](https://github.com/dotnet-architecture/eShopOnWeb/blob/master/src/ApplicationCore/Specifications/BaseSpecification.cs#L7-L55)
* **Де видно принцип:** Універсальний репозиторій працює з абстракцією `ISpecification<T>`, яка інкапсулює критерії фільтрації (`Criteria`), включення пов'язаних сутностей (`Includes`), сортування (`OrderBy`) та пагінацію (`Skip`/`Take`). Клас репозиторію закритий для змін, а логіка вибірки даних відкрита для розширення через створення нових класів-специфікацій.
* **Переваги для підтримки:** Усувається дублювання складних LINQ-запитів у сервісах і відпадає потреба постійно додавати нові методи пошуку (`GetByBrand`, `GetByTypeAndPrice` тощо) до інтерфейсу та реалізації репозиторію.
* **Що зміниться при додаванні нової функції:** При появі нового фільтра в каталозі товарів (наприклад, фільтрації за акційною ціною) створюється новий клас специфікації (успадкований від `BaseSpecification<CatalogItem>`), тоді як код репозиторію залишається незмінним.

## 3. Пропозиція рефакторингу для найгіршого прикладу

**Обраний приклад:** Клас `LoggerConfiguration` (`src/Serilog/LoggerConfiguration.cs`).  
**Суть проблеми:** Клас одночасно накопичує конфігураційні параметри з різних підсистем (приймачі, фільтри, збагачувачі, правила деструктуризації, рівні логування) і самостійно виконує складну збірку ланцюжка декораторів `ILogEventSink` у методі `CreateLogger()`.

**Рішення:** Розділити відповідальності між двома спеціалізованими класами:
1. **`LoggerOptions`** — модель даних, яка зберігає лише налаштування, зібрані під час конфігурації (списки приймачів, фільтрів, збагачувачів та мінімальний рівень).
2. **`LoggerPipelineBuilder`** — окремий будівельник, який приймає `LoggerOptions` та відповідає виключно за конструювання ланцюжка приймачів (`SafeAggregateSink` $\rightarrow$ `AggregateSink` $\rightarrow$ `FilteringSink`) і створення екземпляра `Logger`.

### Код після рефакторингу

```csharp
public sealed class LoggerOptions
{
    public List<ILogEventSink> LogEventSinks { get; } = new();
    public List<ILogEventSink> AuditSinks { get; } = new();
    public List<ILogEventEnricher> Enrichers { get; } = new();
    public List<ILogEventFilter> Filters { get; } = new();
    public LogEventLevel MinimumLevel { get; set; } = LogEventLevel.Information;
}

public sealed class LoggerPipelineBuilder
{
    public Logger Build(LoggerOptions options)
    {
        ILogEventSink sink = options.LogEventSinks.Count > 0
            ? new SafeAggregateSink(options.LogEventSinks)
            : new SafeAggregateSink(Array.Empty<ILogEventSink>());

        bool hasAuditing = options.AuditSinks.Count > 0;
        if (hasAuditing)
        {
            var combinedSinks = new List<ILogEventSink> { sink };
            combinedSinks.AddRange(options.AuditSinks);
            sink = new AggregateSink(combinedSinks);
        }

        if (options.Filters.Count > 0)
        {
            sink = new FilteringSink(sink, options.Filters, hasAuditing);
        }

        return new Logger(sink, options.Enrichers, options.MinimumLevel);
    }
}

public class LoggerConfiguration
{
    private readonly LoggerOptions _options = new();
    private readonly LoggerPipelineBuilder _builder = new();
    private bool _loggerCreated;

    public LoggerConfiguration AddSink(ILogEventSink sink)
    {
        _options.LogEventSinks.Add(sink);
        return this;
    }

    public LoggerConfiguration AddFilter(ILogEventFilter filter)
    {
        _options.Filters.Add(filter);
        return this;
    }

    public Logger CreateLogger()
    {
        if (_loggerCreated)
        {
            throw new InvalidOperationException("CreateLogger() can only be called once.");
        }

        _loggerCreated = true;
        return _builder.Build(_options);
    }
}
```

**Очікуваний ефект рефакторингу:** Логіку побудови конвеєра приймачів (`LoggerPipelineBuilder`) тепер можна тестувати ізольовано від Fluent API конфігурації, а додавання нових етапів обробки логів не перевантажуватиме клас `LoggerConfiguration`.

## 4. Висновки

Аналіз репозиторіїв **Serilog** та **eShopOnWeb** показав, що дотримання принципів **SRP** та **OCP** є основою гнучкості й довговічності промислових C#-проєктів. Найкраще ці принципи проявляються в ядрі архітектури через вузькоспеціалізовані інтерфейси та патерни (`ILogEventSink`, `ITextFormatter`, `ISpecification<T>`), які дозволяють масштабувати систему новими форматами, сховищами чи правилами вибірки без редагування базового коду. Водночас навіть у зрілих open-source проєктах виникають точкові порушення SRP у «склеювальних» класах конфігурації та ініціалізації (`LoggerConfiguration`, `Program.cs`), де накопичується керування багатьма підсистемами. Такі компроміси зазвичай зумовлені зручністю Fluent API для кінцевого користувача бібліотеки або швидкістю налаштування точки входу застосунку. Проте зі зростанням складності подібних класів їх своєчасне розділення на окремі конфігураційні моделі та будівельники знижує зв'язаність коду і спрощує супровід системи.

## 5. Відповіді на контрольні запитання

### 1. Як відрізнити окрему відповідальність класу від просто великого обсягу коду?
Окрема відповідальність визначається не кількістю рядків чи методів, а **єдиною причиною для змін** (за визначенням Роберта Мартіна — єдиним актором або бізнес-роллю, якій підпорядкований клас). Великий за обсягом клас може мати одну відповідальність, якщо всі його методи працюють із тими самими даними та змінюються лише в межах одного бізнес-завдання (наприклад, складний математичний парсер або форматер). Натомість навіть невеликий клас на 80 рядків порушує SRP, якщо він одночасно валідує вхідні дані, виконує SQL-запит до бази даних і відправляє email-сповіщення.

### 2. Які ознаки в коді найкраще підтверджують дотримання OCP?
На дотримання принципу відкритості/закритості вказують такі ознаки:
* ключові модулі системи залежать від **абстракцій** (інтерфейсів або абстрактних базових класів), а не від конкретних реалізацій;
* нова поведінка додається шляхом створення **нових класів** (стратегій, специфікацій, декораторів, обробників подій) та їх реєстрації через DI або плагіни, без модифікації існуючого перевіреного коду;
* у коді відсутні розгалужені конструкції `if-else` або `switch` за типом об'єкта чи переліком (`enum`), які доводиться редагувати щоразу при появі нового варіанта поведінки.

### 3. Чому для аналізу SRP/OCP важливо дивитися не лише на інтерфейси, а й на місця розширення системи?
Наявність інтерфейсу сама по собі не гарантує дотримання OCP: якщо інтерфейс занадто широкий (порушує ISP) або якщо в місцях розширення (фабриках, конфігураторах, точках підключення плагінів) усе одно доводиться вручну дописувати гілки `switch` для кожного нового класу, принцип OCP фактично не працює. Крім того, саме в місцях розширення та композиції об'єктів часто концентруються порушення SRP (як у прикладі з `LoggerConfiguration` або `Program.cs`), коли один клас бере на себе відповідальність за знання про всі конкретні реалізації в системі.

### 4. Які ризики виникають, якщо застосовувати рефакторинг «під патерн» без реальної потреби?
Передчасне або надмірне впровадження абстракцій і патернів проєктування (*over-engineering*) призводить до таких ризиків:
* **Зростання складності коду та зниження читабельності:** замість прямолінійної та зрозумілої логіки розробник змушений переходити через десятки дрібних інтерфейсів, фабрик і обгорток.
* **Сповільнення розробки (порушення принципу YAGNI):** витрачається час на проєктування точок розширення для сценаріїв, які в реальному проєкті можуть ніколи не знадобитися.
* **Помилкові абстракції:** якщо патерн обрано до того, як стали зрозумілими реальні вимоги до змін, створена абстракція виявиться незручною, і при появі нової функції доведеться переписувати всю ієрархію класів.
